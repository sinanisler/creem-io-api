== Security & Access Control ==
- Fix refunded-then-repurchased users being permanently excluded from role reconciliation: process_sale() existing-user branch updated creem_sale_id / creem_sale_data / roles on a re-purchase but did NOT clear the creem_refunded flag set by a prior handle_refund() (remove_roles path). The reconciler (check_existing_subscriptions) excludes users via the `creem_refunded NOT EXISTS` clause (the BUG 1 fix), so the stale flag meant the user was never reconciled again — a later PAUSE of the NEW subscription was never applied (the customer kept the product roles during the pause instead of being downgraded to default_roles), and admin product_roles reconfigurations were not reconciled either. Cancellation/expiry was still caught by the cron transaction loop (step 7) when a recent transaction existed, so this was a narrow but real silent leak with no log line. The flag (and creem_refunded_date) is now cleared when a legitimate new sale is processed and the stored refunded sale_id differs from the current sale_id, mirroring the cron post-process block that clears the end-date meta on renewal. Side effect: the dashboard "Active Subscriptions" count and the reconciler batch selection (which both key off creem_refunded) now correctly re-include re-purchased users instead of under-counting them. No behaviour change for the normal active-user sale, for users who are still refunded (the flag stays set until they actually re-purchase), or for the delete_account refund path (the user + meta are gone anyway). The guard `$stale_refunded_sale !== $sale_id` is also defensive against the impossible-in-practice case of a refunded sale_id reappearing as a non-refund transaction (flag preserved, conservative). Compatible with all three readers of creem_refunded (reconciler NOT EXISTS, handle_refund per-sale `=== $sale_id` idempotency, dashboard NOT IN subquery). (BUG 3)
- Fix handle_refund() (remove_roles) leaking access when the refunded user is PAUSED: it used the product-aware remove_product_roles(), which falls back to creem_assigned_roles — but creem_assigned_roles intentionally stores the ACTIVE entitlement (the product roles), NOT the default_roles the user actually holds during a pause. So refunding a paused user (who holds default_roles, not the product roles) removed nothing, and because the reconciler then excludes the user via creem_refunded NOT EXISTS, the default_roles leaked silently and permanently with no log line. The remove_roles branch now converges the user to ZERO plugin-managed roles via apply_expected_roles($user_id, [], $managed_union) — the exact same pattern already used by handle_subscription_change()'s remove_roles branch — so active->refunded and paused->refunded behave identically (matching active->canceled / paused->canceled). managed_union spans the active entitlement ∪ all_configured_product_roles() ∪ default_roles, so non-plugin roles are never touched. creem_assigned_roles is intentionally left untouched (like handle_subscription_change) so the renewal-redirect logic is unaffected. No behaviour change for the normal active-user refund.
- Complete BUG 2 (orphan-role removal) in check_existing_subscriptions(): the reconciler's managed_union was built from the live product's entitlement ∪ all_configured_product_roles() ∪ default_roles, which covers every CURRENTLY-configured role — but a role the admin removed from EVERY product config is no longer in all_configured_product_roles(), so it fell out of the managed universe and survived on the user forever. Worse, the reconciler then overwrote creem_assigned_roles with the new entitlement, erasing the record that the role was ever plugin-granted, which made it unremovable even at subscription end (handle_subscription_change() derives its $entitlement from creem_assigned_roles). managed_union now ALSO includes the user's own stored creem_assigned_roles, so any role the plugin actually granted to that user is removable while it is no longer expected. Mirrors handle_subscription_change(), whose $entitlement already comes from creem_assigned_roles. A role still legitimately expected is in $expected and is therefore protected from removal; non-plugin roles remain untouched. This is the exact "admin reconfigured the product_roles mapping" scenario BUG 2 (changelog) claimed to handle but only partially did.
- Fix reconciler re-granting access after a refund (remove_roles path): check_existing_subscriptions() selected the batch with creem_sale_data EXISTS + creem_subscription_status NOT EXISTS/NOT IN ENDED, but the refund path removes the roles WITHOUT writing creem_subscription_status. A refunded user therefore re-entered the reconciler batch and, whenever the live Creem subscription was still 'active' (a refund of courtesy without an explicit cancellation), apply_expected_roles() re-granted the product roles on the next cron run — silently undoing the refund within one cycle. The dashboard "Active Subscriptions" SQL already excluded creem_refunded; the reconciler now does too via a NOT EXISTS clause on creem_refunded, so the two paths can no longer disagree. (BUG 1)
- Fix orphan plugin roles never being removed in the self-heal paths (reconciler + subscription-end): managed_union was built from the CURRENT product's entitlement + default_roles only, so a role the plugin had granted for a PREVIOUS product (a user downgraded from Pro to Basic without a new transaction, e.g. a subscription.update product change on Creem with no charge, or after the admin reconfigured the product_roles mapping) was not in the managed universe and was never removed — a silent access leak with no log line (removed=[]). managed_union now also includes every role configured under product_roles[] for ANY product (new all_configured_product_roles() helper), so any role the plugin could ever grant is removable when it is no longer expected. Applied to both check_existing_subscriptions() and handle_subscription_change(). (BUG 2)
- Fix expired subscriptions retaining access: $ENDED_STATUSES excluded 'expired' and 'past_due' based on the (false) assumption they were never returned by the Creem API. The official API contract (docs.creem.io CLI enum + subscription.* webhooks) lists both as real, queryable statuses, and 'expired' means "current_period_end_date reached without a new payment" — i.e. access should end. Added 'expired' to $ENDED_STATUSES so expired subscribers are revoked at period end instead of keeping full access until Creem flips the status to 'canceled'. 'past_due' is intentionally NOT added: it means a renewal payment failed and Creem is retrying (dunning), so access is retained during dunning by policy; it is also kept out because $ENDED_STATUSES drives the renewal redirect and the reconciler batch selection too, and adding it would redirect dunning customers to the renewal page and drop them from role reconciliation. Corrected the stale "the API never returns 'expired' or 'past_due'" comment that caused the regression.
- Fix paused -> canceled access leak: when a subscription went paused (downgraded to the default role(s)) and then canceled, handle_subscription_change() removed only the product roles via remove_product_roles(), but a paused user holds the default_roles — not the product roles — so nothing was removed and the default_roles leaked past cancellation. The remove_roles branch now converges the user to ZERO plugin-managed roles (active entitlement ∪ default_roles) via apply_expected_roles(), making active->canceled and paused->canceled behave identically. Non-plugin roles are never touched.
- Fix refunded sales creating users when "Handle Refunds" is OFF: the refund-detection block was entirely gated by the handle_refunds toggle, so a full-refund/chargeback transaction with the toggle off fell through to process_sale() and created/re-granted access for a refunded purchase. Added an unconditional transaction_is_full_refund() guard before process_sale() so a refunded sale is never processed as a fresh sale, regardless of the toggle.
- Review hardening: process_sale() existing-user branch now keeps creem_assigned_roles in sync with the granted roles — fixes an access leak where, after upgrading from a product with a per-product role mapping to one without (using default_roles), a later refund/cancel could fail to revoke the default role because remove_product_roles() fell back to a stale creem_assigned_roles. Billing customer_id resolution extracted into a shared resolve_customer_id() helper (used by both the shortcode and the AJAX endpoint, so they can't drift). The billing-link JS validates that the returned portal URL is http(s) before opening it (defense against a non-http URL from a compromised/malformed API response). Documented the default-role coupling on resume (paused->active removes the default role granted during the pause).
- Fix partial refunds fully revoking access: any refunded_amount > 0 (even a few cents on a much larger amount) triggered full role removal / account deletion. Now uses the Creem transaction `status` field: revoke only on a full refund (status=refunded) or a chargeback (status=chargeback); partial refunds (status=partially_refunded) are logged and access is retained. Falls back to refunded_amount >= amount_paid when status is absent.
- Fix role reconciliation being skipped for products that use default_roles: check_existing_subscriptions() derived the expected roles only from product_roles[product_id] and skipped reconciliation entirely when no per-product mapping existed ($expected === null). A downgrade from a product with specific roles to a product using default_roles therefore left the old product-specific roles in place forever. The reconciler now falls back to default_roles, mirroring exactly how process_sale() derives roles, so assignment and reconciliation stay symmetric.
- Coverage: check_existing_subscriptions() now uses a rotating offset (creem_existing_subs_offset) instead of always inspecting the first 50 users by login. With more than 50 active subscription users, those beyond the first 50 were never reconciled (upgrade/downgrade) or checked for expiry through this path. The offset advances each run and wraps to 0 at the tail; cleaned up on uninstall via the creem_% option catch-all.
- Fix role not removed at subscription expiry: extract email from subscription (REST customer is ID/empty), read flat JSON (no more "attributes"), "end of period" rule (revoke only after current_period_end_date has passed), fix cancelled->canceled typo, define undefined log variables ($ends_at/$cancelled/$refunded_at)

== Bug Fixes ==
- Fix handle_refund() log spam when the refunded user's account is already gone: the user_not_found branch returned WITHOUT recording the sale_id in the global creem_processed_refund_sale_ids set, so (unlike handle_subscription_change(), whose own user_not_found branch was already fixed at B3) a refund whose user was deleted by a prior subscription-end (delete_account), by an earlier refund (delete_account), or by an external process re-ran on every cron cycle and logged "Refund processing skipped: User not found" each time while the transaction stayed in the fetch window. The branch now calls add_processed_refund_sale_id() before returning, mirroring handle_subscription_change() exactly (the global idempotency set is the only guard that survives account deletion, since the per-user creem_refunded meta is gone with the account). Same accepted trade-off as the sub-end path: a genuinely deleted account is the terminal state. (completes B3 for the refund path)
- Fix renewal redirect loop on a deleted renewal page: wp_redirect(get_permalink($renewal_page_id)) with a trashed/missing page passed false to wp_redirect(), emitting an empty Location header that could loop the expired subscriber on every frontend page. The permalink is now validated first and the redirect is skipped if it is falsy.
- Fix dashboard "Active Subscriptions" counting refunded (remove_roles) users: the refund path removes roles without writing creem_subscription_status, so a refunded-but-not-deleted user was still matched by the active-subs SQL. The query now also excludes users carrying a creem_refunded meta.
- Fix subscription-end log spam after account deletion: handle_subscription_change() only had a per-user creem_subscription_status idempotency guard, which sits AFTER get_user_by(). With subscription_cancellation_action=delete_account the first run deletes the account, so every subsequent cron run hit get_user_by() => null and logged "Subscription change processing skipped: User not found" for every ended-subscription transaction still in the fetch window. This is the exact same bug class as the refund path (B3), which was fixed with a global creem_processed_refund_sale_ids set but never applied to the subscription-end path. Added a parallel global set creem_processed_sub_end_sale_ids (capped at 1000, FIFO, keyed by sale_id so the legitimate end -> renew -> end cycle is never blocked, cleaned up on uninstall via the creem_% catch-all), checked at the top of handle_subscription_change() and recorded on success and in the user_not_found branch (covers the cross-path case where a refund with delete_account removed the account and a later renewal transaction's ended subscription re-triggers the end path).
- Fix new users being unreachable when the Welcome Email is disabled: wp_create_user() does not send any notification, so with "Send Welcome Email" OFF a new customer received a random password and no way to log in. When the welcome email is OFF, wp_new_user_notification($user_id, null, 'user') is now fired so the customer always gets a "set your password" email.
- Fix recurring "User not found" log spam after a refund/subscription-end deletes the account: per-user creem_refunded idempotency cannot work once the user + meta are gone, so the same refunded transaction was logged as "User not found" on every cron run while it stayed in the fetch window. A new global option creem_processed_refund_sale_ids (capped at 1000, FIFO) records every processed refund sale_id and short-circuits re-processing (cleaned up on uninstall via the creem_% catch-all).
- Multi-subscription guard: the plugin assumes one active subscription per customer. If a customer holds 2+ concurrent active subscriptions, it now logs a single "Multiple active subscriptions for customer" warning (with the subscription ids) instead of silently tracking only the latest. Behaviour for the latest subscription is unchanged; concurrent subs are flagged for manual review (documented limitation in the README).
- Fix renewals being re-processed on every cron run forever (purchase_history bloat + corrupted dates): the idempotency check compared only the single stored creem_sale_id, so all but the latest renewal of a subscription were re-processed each run, unboundedly growing creem_purchase_history, churning creem_last_purchase_date with old transactions and inflating the per-run new_sales_processed count. Added a creem_processed_sale_ids set (capped at 200, FIFO) that records every processed sale_id and is consulted before processing; creem_purchase_history is also capped at 100 entries. The new meta is listed in managed_user_meta_keys() so uninstall cleans it up.
- Fix uninstall leaving orphaned usermeta: creem_subscription_ends_at (written by handle_subscription_change) was missing from the delete list in delete_all_plugin_data(), and the catch-all only clears {options}, not {usermeta}. The user meta keys to delete and the uninstall preview UI are now driven by a single source of truth (managed_user_meta_keys()), which also lists the previously-unshown creem_customer_id and creem_subscription_ends_at, so the two lists can never drift apart again.
- Reduce cron noise: transactions whose customer email cannot be resolved (transaction customer is a string ID and the subscription fetch failed / has no customer email) are now skipped with a single concise log instead of failing repeatedly inside process_sale()/handle_refund() with 'invalid_email'. They are retried on the next cron run, so a transient API outage is never permanently lost.
- Fix GitHub auto-update asset name mismatch: $github_asset_name was set to 'creem-io-api.zip' but the release workflow actually publishes 'creemio-api.zip' (verified against the published v0.6 release). The dedicated asset was therefore never matched and the updater always fell back to the GitHub zipball, whose top-level folder structure WordPress cannot rename correctly during auto-update. Now matches the real asset name.
- Fix GitHub auto-update undefined variable: $github_asset_name was not imported via `global` in creem_io_api_check_github_update() and creem_io_api_plugin_info_from_github(), so it was undefined inside both functions (PHP notice) and $expected_asset_name resolved to null, guaranteeing the dedicated-asset branch never matched. Both functions now globalize $github_asset_name.
- Fix GitHub auto-update hardcoded plugin slug in the version-link redirect JS: pluginSlug was hardcoded to 'creem-io-api', so when the plugin is installed under a different folder name (e.g. 'creemio-api') the "View version details" links were never rewritten and opened the Thickbox popup instead of redirecting to GitHub. Now derived dynamically from $plugin_slug (plugin_basename(__FILE__)), matching the PHP side.
- Fix stale subscription-end meta surviving a renewal: when a subscription went canceled -> renewed, check_recent_sales reset creem_subscription_status to the active status but left creem_subscription_ended_date and creem_subscription_ends_at holding the old cancellation dates. Both are now deleted on a successful renewal so the Users page no longer shows phantom end dates.
- Fix primary product meta not updating on renewal/upgrade for existing users: process_sale() updated creem_last_product_* and creem_sale_id but not the primary creem_product_name/creem_product_id, so the Users page and Product Breakdown kept showing the original product until the next reconciliation cycle. The primary product meta is now updated in the existing-user branch, keeping process_sale() and the reconciler in sync.
- Fix sales_limit being consumed by one-time payments: the pagination loop gated on count($transactions) < $sales_limit, which counted every fetched transaction including type=payment (one-time) that are then skipped before processing. A store with many recent one-time payments and a low sales_limit could push older subscription transactions out of the fetch window so they were never processed. The loop now counts only processable (non-payment) transactions toward the budget, with a hard max_pages safety cap (10 pages / up to 1000 transactions) so a flood of one-time payments can't paginate unboundedly.
- Fix renewal transactions being re-processed on every cron run forever: process_sale() updated creem_last_sale_id for existing users but never creem_sale_id, so the idempotency check (stored sale_id === current sale_id) kept re-running each renewal every cycle (wasted subscription fetches + inflated "new sales processed" metric). creem_sale_id, creem_sale_data and the purchase history are now updated for existing users regardless of whether new roles were added; the subscription_id is stable across renewals so refreshing the stored sale data is safe.
- Fix log_limit and user_list_per_page being reset to defaults whenever the main Settings page was saved: those two fields are not part of the Settings form, so save_settings() fell back to its defaults and wiped values the user had configured on the Logs/Users sub-pages. The existing values are now preserved when the fields are absent from the POST.
- Fix dashboard "Refunds Processed" being windowed and over-counted: it was computed from rotating logs (capped at log_limit + 30-day rotation) and matched any log type containing "refund" (including "Refund processing skipped"), yet the card was labeled "All time". A persistent creem_refund_count option is now incremented once per actually-processed refund (gated by the per-sale idempotency guard), giving a true all-time count. "Recent Activity (24h)" stays log-based since a 24h window is always inside the rotation window.
- Fix github-update.php hardcoding the install folder as 'creem-io-api': the update check (pre_set_site_transient_update_plugins, runs on every admin page load) called get_plugin_data() on WP_PLUGIN_DIR.'/creem-io-api/creemio-api.php', which doesn't exist when the plugin is installed under a differently named folder (e.g. 'creemio-api'). This produced a file_get_contents() "No such file or directory" warning (and the resulting "headers already sent" cascade) on every admin screen, and also broke auto-updates since the transient response key must equal the real plugin basename in active_plugins. $plugin_slug/$plugin_file are now derived from plugin_basename(__FILE__); the GitHub release asset name is kept as a fixed constant independent of the install folder.
- Fix "Handle Subscriptions" toggle breaking the pipeline when OFF: decouple the subscription fetch from the toggle (the subscription is the only source of email+product since a transaction carries no product and customer is a string ID); the toggle now gates only the auto-revoke-on-end logic. Previously, with the toggle OFF, no user was created (invalid_email every cron) and refunds couldn't resolve the user
- Fix dashboard "Active Subscriptions" always showing 0: the SQL matched LIKE '%subscription_id%' but the stored transaction JSON uses the key "subscription" -> now matches '%subscription%'
- Idempotency guards to stop re-processing the same transactions every cron run: handle_refund() early-returns if THIS sale was already refunded (tracked per-sale by storing the sale_id in creem_refunded, so a refund -> repurchase -> refund cycle still processes the new refund); handle_subscription_change() early-returns if the subscription was already processed as ended (prevents log spam, re-stamped dates and inflated dashboard metrics)
- Fix products pagination in fetch_products(): Creem returns pagination.next_page, not next_page_number (only the first page was loaded when a store had >50 products)
- Fix dashboard "Total Sales Processed" stat: reuse the existing total_users COUNT (+0 queries, -1 get_option) instead of counting rotating logs; drop the never-written creem_processed_sales fallback
- Refund: resolve email from the subscription; unify subscription statuses (canceled/expired/scheduled_cancel/past_due/unpaid) through the $ENDED_STATUSES constant
- Renewal: reset creem_subscription_status on a successful (re)payment so an expire->renew->expire cycle is caught again and the "Active Subscriptions" metric stays accurate
- Fix "Active subscriptions" SQL query (IN on terminal statuses) and renewal redirect (in_array)

== Hardening ==
- Harden save_settings() default_roles against a non-array POST value: array_map() requires its array argument to actually be an array and fatals (TypeError) on PHP 8 if default_roles is sent as a scalar. It was the only array_map() over a POST field without an is_array() guard (product_roles and product_auto_create already had one). The normal checkbox form always sends default_roles[] (an array) or omits the field, so this is unreachable in normal use; now guarded with is_array() so a malformed request degrades to "no default roles" instead of a fatal. No behaviour change for the normal form. (M4)
- Harden the activity-log readers against a non-array option value: every write path (log_activity(), clear_logs()) stores an array, so under normal operation creem_api_logs is always an array. A corrupted/migrated option holding a non-array value would make array_slice()/foreach fatal on PHP 8 on the Dashboard and API Logs pages (the write side in log_activity() was already guarded). A new private get_logs() helper centralizes the is_array guard on the read side and is now used by the four readers (dashboard_page, get_dashboard_statistics, logs_page, get_uninstall_data_statistics). The first-write detection in log_activity() (get_option(..., null) === null, which creates the option with autoload=no) is intentionally left on the raw get_option() call: returning array() there would make the first write go through update_option() and create the option with autoload=yes, silently breaking the autoload=no optimization. (M4)
- Harden save_settings() sales_limit with a server-side min clamp (max(1, ...)). It was the only numeric setting without one: cron_interval (max 30), log_rotation_days (max 1) and user_list_per_page (max 1) were all clamped, but a direct POST or a migrated config with sales_limit=0 made the do-while fetch loop run a full page anyway (processable_count exceeds 0 immediately). Now consistent with the HTML min=1 and with the other numeric settings. No behaviour change for normal values (1-200). (M3 class)
- Harden test_api_connection() to accept BOTH list shapes ({items,...} and the documented {data,has_more}) instead of only {items}, so a future Creem API migration to the documented shape does not turn a valid API key into a false "Unexpected response format" error. (M1)
- Harden process_sale() new-user branch against a null user after wp_create_user(): bail with a WP_Error instead of fatal-ing on $user->set_role() in the rare race where the account is removed between creation and the lookup. (M2)
- Clamp log_rotation_days to a minimum of 1 in save_settings(): a value of 0 would set the cutoff to "now" and wipe every log entry on each write. cron_interval and user_list_per_page already had the clamp; this one did not. (M3)
- Harden the Users page Assigned Roles cell against non-array creem_assigned_roles JSON: implode() on a null json_decode() emitted a PHP warning. Now falls back to 'N/A'. (M4)
- Harden the billing-link click handler against popup blockers: window.open() inside an async fetch runs outside the user-gesture window and is frequently blocked; it now falls back to a same-tab redirect (window.location.href) when the new tab is blocked, so the portal is always reachable. (M5)
- Harden transaction_is_full_refund() against partial refunds reported under status='refunded': the docs only document transaction status='refunded' for FULL refunds (refunded_amount == amount_paid); the status of a partially refunded transaction is undocumented ('partially_refunded' is an ORDER status, not a transaction status). If Creem ever marks a transaction 'refunded' while refunded_amount < amount_paid, it is now treated as a PARTIAL refund (access retained) instead of revoking everything. Purely protective: documented full refunds are unaffected.
- Defensive dual-shape list parser: the plugin read transactions/products search responses as {items, pagination.next_page} with page_number/page_size, but the only list shape documented by Creem is {object:'list', data:[...], has_more:bool} with a `limit` param. Both are now accepted via a new parse_creem_list() helper (items/data + pagination.next_page/has_more). If neither shape is recognized, an explicit "Unexpected API list response shape" activity log is emitted instead of the plugin silently processing zero rows — so a future API change can never break transaction processing invisibly. Applied to both check_recent_sales() (transactions) and fetch_products() (products); the now-unused parse_creem_transactions() passthrough was removed.
- Harden log_activity() against a corrupted/migrated activity-log option: get_option() can return a non-array value, which would make array_unshift()/array_filter() fail and break all logging. The value is now reset to an empty array when it is not an array.
- Harden fetch_products() pagination: the do-while loop had no page cap and assigned $page_number directly from pagination.next_page (fragile if Creem returns next_page as a bool/URL instead of a page number), unlike check_recent_sales() which already had a max_pages cap and drives its own counter. A malformed API response could loop the admin AJAX handler forever. Now mirrors the cron path: own page counter, next_page used only as a "has more" truthiness flag, hard cap of 20 pages (1000 products).
- Harden send_welcome_email(): get_password_reset_key() can return WP_Error; interpolating it into the password_reset_url would raise a fatal "Object of class WP_Error could not be converted to string" under PHP 8 while building the welcome email. Now falls back to wp_lostpassword_url() when key generation fails so the new user can still set a password.
- Refund detection hardened into transaction_is_full_refund(): still revokes on status=refunded/chargeback and the refunded_amount>=amount_paid fallback, now also recognises a standalone refund transaction (type=refund) defensively. Partial refunds retain access. NOTE: confirm the exact refund field shape from debug logs and extend the helper if Creem uses a different marker.
- Hardening: subscription_id is now rawurlencode()d in the fetch_subscription() URL.
- Fix fetch_subscription() passing a non-string error to WP_Error: it read $data['error'] directly, which can be an array in some API responses. It now uses get_api_error_message() (already used everywhere else) so the message is always a string.
- Hardening get_first_name_from_email(): strpos($email, '@') could return false (no '@'), which is invalid as a substr length and raises a PHP 8 deprecation. Added an explicit false guard that falls back to the whole email local part.
- Hardening process_sale(): added is_array() check on $product_roles[$product_id] before using it as the roles list, so corrupted/migrated non-array data cannot make set_role() receive a single character of a string.
- Harden "Active Subscriptions" SQL: the LIKE matched the bare word '%subscription%', which could also match product names/values containing that word. It now matches '%"subscription"%' to target the JSON key precisely.
- Harden cron scheduling: schedule_cron(), deactivate() and delete_all_plugin_data() now use wp_clear_scheduled_hook() instead of wp_next_scheduled() + wp_unschedule_event(), which removed only a single event and could leave duplicates behind (double-activation, restored DB). schedule_cron() in particular runs on every settings save, which is where duplicates would otherwise accumulate.
- Hardening: null-check get_current_screen() in admin_styles() (could throw a fatal on PHP 8 in admin contexts where the screen object is null); clamp cron_interval server-side to a minimum of 30 seconds in add_custom_cron_interval() and save_settings() (was HTML-only min, so a 0/negative value could make the cron run excessively). No behavior change for normal values.

== Performance ==
- Performance: the creem_api_logs option is no longer autoloaded. It was created with autoload=yes (the update_option default), so the potentially large activity log was deserialized on every page load site-wide. The first write now creates it with autoload=no, and an admin_init migration (ensure_logs_not_autoloaded, not activation-only because WordPress skips activation hooks during auto-updates) flips existing installs. Added a Debug Mode setting (default off): raw API payloads (subscription/transaction/sale responses) are replaced with compact summary fields unless Debug Mode is enabled, keeping the log small while preserving diagnosability on demand.
- Performance: memoize subscription fetches inside fetch_subscription() via a per-request $subscription_cache (keyed by subscription_id, caching successes, WP_Errors and nulls). This replaces the local $fetched_subscriptions cache in check_recent_sales() and now also benefits check_existing_subscriptions() (users sharing a subscription_id in the same batch fetch once). The cache is cleared at the start of check_existing_subscriptions() to isolate the reconciler phase from the transaction loop, so a cancellation between the two phases is never masked.
- Performance: memoize subscription fetches within a single cron cycle. Multiple recurring transactions (initial charge + renewals) share the same subscription_id, but each was triggering a separate GET /v1/subscriptions call every cron run. The result (including null) is now cached per subscription_id for the duration of the cycle, so each subscription is fetched at most once per run.

== Features & UX ==
- Paused subscriptions: a subscription whose Creem status is `paused` is now downgraded to the configured default role(s) (removing the product roles) and restored to the product role(s) when it resumes. `paused` is intentionally NOT an ended status, so paused users stay in the reconciliation batch (auto-restore on resume) and are never redirected to the renewal page. Implementation uses a new symmetric apply_expected_roles() helper that converges the user to the expected role set among the plugin-managed universe (active entitlement ∪ default_roles) every run, so the active↔paused transition is reversible and idempotent (no flip-flop). creem_assigned_roles always stores the ACTIVE entitlement so resume + remove_product_roles work. Dashboard "Active Subscriptions" now also excludes paused users. The Settings "Default User Roles" description mentions paused users.
- Upgrade/downgrade now applies immediately: process_sale() removes the previous product's roles before granting the new ones when the product changes (old vs new creem_product_id), instead of waiting for the next reconciliation batch.
- Billing link shortcode: the portal link is now generated ONLY when the user clicks the button (via a new ajax_billing_link endpoint), so loading a page with [creem_billing_link] no longer calls the Creem API on every page load (rate-limit friendly) and never wastes a single-use token. The customer_id is resolved server-side from the logged-in user's own meta (never from the client), so one user cannot request another's portal link. A failed API call shows a visible fallback ("Billing temporarily unavailable") instead of a broken link.
- Dashboard "Total Sales Processed" renamed to "Customers Created" to reflect what it actually counts (= number of users created from a Creem sale).
- Renewal redirect: skip login/registration pages (wp-login.php, wp-register.php, wp-signup.php) plus AJAX and REST requests so expired subscribers are never locked out of authentication; add a creem_skip_renewal_redirect filter so third-party code (e.g. WooCommerce cart/checkout) can whitelist additional reachable pages.
- Skip one-time payments (type=payment) early in check_recent_sales() before any subscription fetch; report them as one_time_skipped in the "Cron completed" log instead of spamming invalid_email/missing_product_id errors every cron run
- Product-aware role removal via remove_product_roles() helper (fallback to creem_assigned_roles); creem_assigned_roles left untouched so the renewal redirect keeps working
- Upgrade/downgrade: reconcile each user's creem roles to their current subscription product in check_existing_subscriptions (idempotent + self-healing; removes old-tier roles, adds new-tier ones). process_sale left untouched; one-time sales are skipped automatically

== API Contract & Documentation ==
- Docs/contract accuracy (verified against the live REST API + OpenAPI on api.creem.io): the plugin polls REST only (no webhooks), so $ENDED_STATUSES is now derived from the documented SubscriptionEntity.status enum (active, canceled, unpaid, paused, trialing). Trimmed to the two terminal REST statuses 'canceled' and 'unpaid'; removed 'expired' and 'scheduled_cancel', which are never returned by the REST subscription endpoint (ended subscriptions come back as 'canceled' — confirmed against production data) and had been added from webhook/CLI references. creem_period_ended() still gates 'unpaid', so a customer is only revoked after the paid period elapses. Rewrote the $ENDED_STATUSES and parse_creem_list() comments, which previously cited subscription.* webhooks and mislabelled the {items,pagination} list shape as "empirical" — it is the documented shape on products/transactions/subscriptions. No behaviour change in practice: the removed statuses were unreachable via REST. Added an "API reference (consumed endpoints)" section to the README with redacted response shapes.
- Remove inert non-existent subscription statuses from $ENDED_STATUSES: 'expired' and 'past_due' are never returned by the Creem API (kept 'canceled','scheduled_cancel','unpaid'); zero behavior change
